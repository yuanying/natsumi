# 0016. カードを開く操作と、キャラクターが動くこと

- Date: 2026-09-18
- Status: Accepted

## Context

[ADR 0010](0010-mac-app-structure.md) が、Mac の画面に出るものの仕様を決めている。その作り方は
[ADR 0015](0015-mac-ui-passive-view-tree.md) で一本の木の Passive View に置き換えたが、**画面の仕様は変えていない。**
この ADR は、その仕様のうち次の 3 つを、利用者の指示によって改める。

- **確かめる操作の割り当て。** ADR 0010 では、返事の吹き出しと知らせのカードは、本文のクリックでその 1 件を
  既読／確認にして次を前に出し、× で束をまとめて閉じる、という形だった。実際に使ってみると、**本文を読もうとして
  クリックすると消えてしまう。** 長い発言が 120 文字・5 行で切られているので、続きを読みたくて押すのに、
  押すと確かめたことになって次のカードが出てくる。
- **切られた本文の読み方。** 続きは「続きは履歴で」から履歴を開いて読む形しかなかった。返事 1 件を読むために、
  一列とは別のウインドウを開くことになる。
- **大きくなった吹き出しをどこへ伸ばすか。** ADR 0010 は、入らないときはパネルの側（一列の反転、重ねる枚数と
  行数を減らす）で吸収すると決めていた。本文を開いて全文を出すと吹き出しは今までよりずっと大きくなるので、
  どちら側へ伸ばすかと、どこまで削るかを決め直す必要がある。

あわせて利用者から、次の 2 つの要望が出ている。

- 位置が変わるときは、瞬間移動ではなく**走って移動してほしい**（「いい感じにアニメーションすること」）。
- **ポインタがクリックもせずに近くに来たときは、その下の要素をクリックしたいことが多いので、いい感じの間隔で
  そこをどいてほしい。**

## Decision

### 1. × と本文のクリックを入れ替える

返事の吹き出しと知らせのカードで、**同じ規則にする。**

- **本文のクリックは、そのカードを全文に開く。** 既読にも確認にもしない。もう一度クリックすると畳む。
  開いているのは一度に 1 件で、別の本文を開くと前のは畳む。前に出ているカードが入れ替わったときも畳む。
- **× は、その 1 件だけを既読／確認にして、次を前に出す。** 束の最後の 1 件を × で消せば、束は閉じる。
- 「受付中」「考え中」の吹き出しには開く本文が無い。× は今までどおり、次に中身が変わるまで隠すだけである。

「すべて既読にする」「すべて確認する」は、**キャラクターの右クリックのメニューだけになる。** ADR 0010 で
すでに置いてあるものであり、**失われた操作ではなく、移った操作である。** × の tooltip は、その 1 件を消す意味の
文言に直す（「この返事を既読にして次へ」「この知らせを確認して閉じる」など）。

**一覧より古い知らせをまとめた「前の知らせが N 件」の 1 枚だけは例外とする。** このカードには本文が無く、
開くものがないので、今までどおりクリックでまとめて確かめる。× も同じ結果になる。

**サーバーとの契約は変わらない。** `conversation.read`・`notification.ack` のコマンド、requestId、楽観的な反映、
`command.rejected` で戻すこと、切断中の送信を同期後に同じ requestId で送ること、冪等であることは、
すべて ADR 0010・[ADR 0013](0013-read-state-on-the-server.md) のままである。変わったのは、どの操作がどのコマンドを
出すかだけである。

### 2. 「続きは履歴で」は残し、拡大と併存させる

- 切られている間は「続きは履歴で」を出したままにする。履歴への誘導を無くさないのは、**吹き出しは一列の中にあり、
  幅も高さも限られる**ためで、全文が長ければ結局は履歴のほうが読みやすい。
- 開いたカードは全文を出す。ただし**吹き出しの中でスクロールはさせない**（ADR 0010 の決定を守る。フォーカスを
  持たないパネルの中の小さなスクロールは扱いにくく、吹き出しの大きさも読み取りにくい）。
- したがって、**画面に入る範囲まで伸ばし、それでも入りきらなければそこで切り、「続きは履歴で」を出したままにする。**
  行数の梯子は、開いていないときの梯子（`StackBudget.steps`）とは別に、全文の上限から下りてくるものを用意し、
  最後は開いていないときと同じ段に着く。開いたカードが入らなくても、閉じているときより悪くはならない。
- 縦の一列の規則（ADR 0010）はそのままである。開いた吹き出しも列の中に収まり、横はキャラクターの中心にそろえる。
- **ただし、開いたカードは横にも広がってよい。** ADR 0010 は「パネルの幅の上限は入力欄の幅にそろえる」と
  決めていたが、利用者の判断でこれを開いたカードについて取り下げる。縦だけを伸ばすと、同じ本文がいたずらに
  行数を食い、入る分が減るためである。
  - 広がってよいのは**開いた 1 枚だけ**である。閉じているカード・入力欄・キャラクターの印は今までの幅のまま。
  - 上限は**列の幅の 2 倍**とし、画面の左右に余白を残す。読める行の長さには限りがあり、画面が広いというだけで
    1 行を長くしても読みにくくなる。
  - **画面の端にいても同じだけ広がる。** 横にはみ出す分は今までどおり内側にずらし、しっぽはキャラクターの中心を
    指し続ける（しっぽの位置も一緒に動く）。カード 1 枚ごとのウインドウだった間は、開閉のたびにカードが横に
    滑って終わりの位置と食い違うため「列の位置が動かない範囲まで」に制限していたが、舞台（下の「3.」）では
    位置と大きさが同じ時計で動くので、滑ること自体が開閉の動きの一部になる。

### 3. 拡大・縮小はアニメーションさせる: 一枚の舞台の上で

**キャラクターと返事の吹き出しと知らせの束は、1 枚の透明なウインドウ（舞台）の中の View として描く。**
これは ADR 0010 の「吹き出し・知らせの束は、キャラクターのパネルの子ウインドウにする」と
「パネルの枠は配置の計算だけで決める」を、この 3 つについて改める。

はじめは ADR 0010 のまま、カード 1 枚ごとに `NSPanel` を持たせて動かそうとした。**手で動かして、これでは駄目だと分かった。**

- Mac では、ウインドウの枠はレンダーサーバーで補間されない。`animator()` で枠を動かしても主スレッドのタイマーで
  刻むだけで、SwiftUI で動く中身とは別の時計になる。「同じ時間・同じ曲線」を守っても、原理的に同期しない。
- ウインドウは中身を四角く切り取る。枠を先に小さくすれば中身が角で切られ、枠を先に大きくして押さえれば、
  その間の帳簿（いつ確定させるか、どの向きに寄せるか）が要る。
- `withAnimation` で中身を包んでも効かない。`NSHostingView` の root view を外から差し替える形では、
  変更がその transaction の外で起きるためである。
- 吹き出しが伸びると上の知らせのカードは位置が変わるが、別のウインドウなので一緒には動けない。
  1 枚ずつ押さえて後から確定させると、確定の瞬間に跳ぶ。

これらはすべて「動かす対象がウインドウの枠である」ことから来ていた。改めた形は次のとおり。

- **舞台**: 枠のない透明な `NSPanel` を 1 枚だけ持ち、キャラクターのいる画面全体に広げる。層・Space・全画面の扱いは
  ADR 0010 のパネルと同じ（`.nonactivatingPanel`、`floating`、`canJoinAllSpaces`、`fullScreenAuxiliary`）。
  舞台のウインドウが動くのは、キャラクターが別の画面へ運ばれたときと、画面の構成が変わったときだけである。
- **中身**: キャラクター・吹き出し・知らせの束は、舞台の中の 1 本の SwiftUI の木に、配置の計算（`OverlayLayout`）が
  与えた枠で置く。動くのはすべて View の枠であり、Core Animation が 1 つの時計でまとめて補間する。
  枠と中身の同期、角で切られること、列の他のカードが跳ぶこと、走っている間に列がついてくること、
  どれも仕組みとして消える。
- **見せ方は Root が決める。** 描画パスごとに、即座（ドラッグ・倍率の変更・最初の描画・舞台の移動）、
  カードの開閉（0.25 秒、ease-in-ease-out）、走り（距離から決めた時間、同じ曲線）のどれかを選び、
  舞台の View がそれを時間と曲線に変える。Mediator と導出はどれだけかかるかを知らない。
  カードの開閉だけでなく、返事が届いて列が組み変わるときも同じ 0.25 秒で動く。
- カードは、配置が与えた高さで自分の箱を描く（`panelHeight`）。開閉で動く数は 1 つだけになり、
  中身の計測（行数の梯子を決める `probe`）と描かれる大きさは同じ数から出る。
- 舞台の中身は `.animation(_:value:)` で動く。root view の差し替えで渡されても、描画パラメータが変われば動く。
- **走りを途中で止めるとき**（掴まれたとき）は、走りの曲線から「いまどこに見えているか」を計算して、
  そこに即座に置き直す。SwiftUI は途中の値を教えてくれないので、舞台が使う曲線と同じ 3 次ベジエを
  `NatsumiCore` に持ち（`CharacterRun.place`）、両方をそろえる。
- **入力欄・履歴・設定は舞台に入れず、自分のウインドウのままにする。** 入力欄はキーボードを受けるために key に
  なる必要があり、舞台を key にすると、閉じたあとにキーボードを元のアプリへ返す方法が無い。
  入力欄は舞台の子ウインドウとして上に重ね、配置の計算で置く。ADR 0010 の「キーボードのフォーカス」はそのまま
  成り立つ。動くものは舞台の中、キーボードを受けるものは自分のウインドウ、という分け方である。
- しっぽはキャラクターの中心を指し続け、アニメーションの途中でも列は崩れない。

#### 舞台とマウス

舞台は画面全体を覆うので、**マウスをどこで受けるかを Root が決める。** 透明な部分のクリックがウインドウの下へ
抜けることに頼らない（macOS の版によって振る舞いが違う。透明な部分で止めてしまう版がある）。

- 既定では舞台は `ignoresMouseEvents` にし、マウスを受けない。クリックは下のアプリへ抜ける。
- ポインタが、キャラクターと 2 枚のカードの枠（画面の座標）のどれかに入ったら、舞台がマウスを受けるようにする。
  出たら戻す。アニメーションの間は、動く前の枠（走りなら出発点と目的地を囲む箱）も、その時間だけ数に入れる。
- ポインタの位置は、舞台がマウスを受けていない間はグローバルな監視（`.mouseMoved`）で、受けている間は舞台の
  `NSTrackingArea`（`.activeAlways`）で知る。どちらも同じ 1 つの関数へ入り、判定は毎回行う（間引かない）。
  クリックはポインタが乗った直後に来るためである。どく判断のほうは今までどおり間引く。
- キャラクターの枠の中の透明な画素（絵の周り）は、以前は下へ抜けていたかもしれないが、いまは枠ごと受ける。
  ポインタを避けてどく仕組みがその穴を埋める。

#### キャラクターの居場所

キャラクターはもうウインドウではないので、`setFrameAutosaveName` は使えない。Root が画面の座標の原点を
UserDefaults に保存し、無ければ以前の版がウインドウの枠として保存した文字列から読み替える（初回の起動で
場所が変わらないようにするため）。保存するのは今までどおり `.saveCharacterPlace` の指示のときだけである。

### 4. 位置が変わるときは走って移動する

| 場面 | 走るか |
|---|---|
| 画面構成の変化（ディスプレイを抜いた・解像度が変わった）で画面内に戻すとき | 走る |
| ドラッグで動かすとき | 走る（進行方向を向く。手を離したら表情の動作に戻る） |
| ポインタが近づいて、その前からどくとき | 走る（下の 5） |
| 設定で倍率を変えたとき | **走らない。**今までどおり、足もとを保って即座に大きさだけ変える |
| **一列が入らないとき** | **動かない。**一列の側で吸収する（下の「伸ばす向き」） |

**移動の時間は距離から決める**（1 秒あたり 220 ポイント、0.5〜1.3 秒）。曲線は拡大・縮小と同じ ease-in-ease-out。
時間を一定にすると、遠くへ動くほど速くなり、**走る絵が見えないまま着いてしまう**（手で動かして確かめた）。
速さをそろえれば、少しどくときも画面をまたぐときも同じ足どりに見える。走っている間、吹き出しと知らせの束は
同じ舞台の上で同じ時間をかけて動くので、一緒に動いて見える。入力欄と履歴は自分のウインドウなので、
入力欄は配置の計算で追い、履歴は移動が終わってから置き直す。

#### 伸ばす向き: 一列は、余裕のある側へ伸びる

**ADR 0010 の「一列が入らないときはパネルの側を変える」はそのまま残す。キャラクターは一列のためには動かない。**

はじめは逆にして、入らないときはキャラクターが動いて場所を空ける形にした。**これは実際に使って取り下げた。**
一列をいま立っている場所から組んでいたので、開くたびに「まだ足りない」と同じ要求が繰り返し出て、
**キャラクターが少しずつ下がっていき、画面から消えて入力欄と重なった。**
基準を自分の場所に取り直せば直せるが、利用者の判断で、一列のためにキャラクターを動かすこと自体をやめる。

代わりに、**大きくなった吹き出しは、余裕のある向き（上下と左右の両方）へ伸ばす。**

- **どちら側に伸ばすかは、上下の余裕で決める。** 上に入らず下に余裕があれば、一列を反転して下へ伸ばす。
  既定は上（漫画のセリフとして自然な向き）で、反対側のほうが多く置けるときだけ譲る。
  入力欄が反対側で要る高さも数に入れる。
- **行数の段は、上のほうを細かくする。** 入る行数から大きく取りこぼさないためで、余裕のある側を使い切るには、
  段が飛び飛びでは足りない。
- **横にも広げる**（上の「2.」）。1 行に入る文字が増えるので、同じ本文でも要る行数が減り、切られにくくなる。
- それでも入らなければ、今までどおり、重ねる枚数を 0 にし、行数を減らし、最後は知らせの束を出さない。
  切られた分は「続きは履歴で」に残る。

#### 走る絵の出し分けと、落とし方

- **動作の引き方を、表情とは別の筋にする。** 表情から動作を引く表（`AvatarManifest` の対応表）はそのままにし、
  移動中はそれを移動の動作で上書きする。
- 横に動く向きで出し分ける。右へ動くなら `running-right`、左へ動くなら `running-left`。
- **ほぼ真上・真下にしか動かないときは、直前の向きを保つ。** わずかな横のぶれで向きが反転しないようにするためで、
  上下の移動で毎回どちらかを向き直すより落ち着いて見える。
- **落とし方**（利用者が自分のアバターを差し替えられる。ADR 0010）: `running-left` / `running-right` が無ければ
  `running`、それも無ければ**表情の動作のまま**にする。つまり絵は変えず、位置だけ動かす。
  無い動作を指しても読み込みの誤りにはしない。
- 仮の絵（表情ごとの絵文字、`PlaceholderArt`）には走る絵が無いので、位置は動かすが絵は変えない。

### 5. ポインタが近づいたら、どく

- **しばらく留まったらどく。** 近づいた瞬間には逃げない。**1 秒**そこに留まって初めて走って逃げる。
  素早くクリックすれば、今までどおり話しかけられる。
  最初は 0.4 秒にしたが、手で動かしたところ**話しかけようとしても先に逃げられてクリックできなかった。**
  押しに行って狙って押すまでの間より長くする必要がある。
- **行き先は、ポインタから遠ざかる向きへ 1 歩だけ**（キャラクターの幅＋余白の 2 倍）。
  最初は「できるだけ画面の端へ」としたが、手で動かしたところ**遠くへ行きすぎた。**
  どくのは目の前から退くためであり、画面の反対側まで行く必要はない。
- 向きの選び方は、**横に遠ざかる向き → その反対 → 上下**の順に試す。画面の端で行き止まりなら次の候補に移る。
  どの候補でもポインタの前から退けなければ（画面がごく狭いときなど）、**どかない。**
  これで、端にいるときを特別扱いする必要がなくなった（1 歩の移動は、どこにいても同じように効く）。
- **ポインタが離れたら、元の場所へ走って戻る。** どいたのは一時的なもので、覚えている定位置は変えない。
- **どかない場面**: 入力欄が開いている間（キャラクターの下に入力欄があり、そこへ向かうポインタで逃げられたら
  使えない）、ドラッグしている間（本人が掴んでいる）、ポインタが一列のパネル（吹き出し・知らせ・入力欄）の
  上にあるとき（それらはクリックされるためにある）。

#### 行ったり来たりを止める

- **近い／離れたの境を別にする**（近い: 枠の周り 28 ポイント、離れた: 96 ポイント。キャラクターの倍率に合わせる）。
  戻るときも 0.7 秒、離れたままでいるのを待つ。
- **どいている間、ポインタは「戻る先」の周りで見張る。** いま立っている場所で見張ると、どいた直後にポインタから
  離れているので即座に「離れた」となり、戻ったとたんにまた逃げる。戻る先で見張れば、ポインタがそこから
  離れるまで戻らない。

#### ポインタの見張り方

- マウスのイベントの監視に、アクセシビリティの許可は要らない（ADR 0010）。
- `NSEvent.addGlobalMonitorForEvents` は**自分のアプリのウインドウの中では発火しない。** 舞台がマウスを受けている間は
  舞台の `NSTrackingArea`（`.activeAlways`）が代わりに知らせる（上の「舞台とマウス」）。
  アプリは前面にならないので、`.activeAlways` でなければ届かない。
- **`.mouseMoved` は大量に来るので、どく判断は Root で間引く**（0.04 秒に 1 回）。毎回配置を計算し直さない。
- **見張りは Root が持ち、Mediator には意味のイベントだけを渡す。** Mediator が受け取るのは「ポインタが留まった」
  「離れた」の 2 つで、生の座標の流れは渡さない。どこへどくかを決めるためにポインタの位置が 1 回だけ要るので、
  「留まった」のイベントだけがその 1 点を運ぶ。見張る範囲（戻る先の枠）は Mediator が指示として Root に渡す。

## Consequences

- 本文のクリックで確かめられなくなった。1 件ずつ確かめるには × を押す。押す場所は小さくなるが、
  **読もうとして消える**ことは無くなる。
- 「すべて既読／すべて確認」は右クリックのメニューにしかない。メニューバーからも同じことができる。
- 開いたカードが入らないときは、行数で切られて「続きは履歴で」が残る。全文がどうしても必要なら履歴を開く。
  何行まで入るかは画面と倍率で変わるので、同じ返事でも Mac によって切れ方が違う。
- 一列のためにキャラクターは動かないので、開いた本文が画面に入らなければ、その分は行数で切られる。
  置いた場所によって、同じ返事でも切れ方が違う。
- 開いたカードだけが広いので、開くと列の幅がそろわなくなる。開いている間だけのことであり、
  閉じれば元の幅に戻る。
- 開いた吹き出しは、置いた場所によってキャラクターの上にも下にも出る。返事が来るたびに向きが変わることは
  ない（向きは余裕で決まり、余裕は置いた場所で決まる）が、キャラクターを画面の上下に動かすと向きが変わる。
- どいている間は、定位置を保存しない。アプリを終了するのがどいている最中だと、次に起動したときの場所は
  どく前の場所になる。
- `.mouseMoved` のグローバルな監視を常時持つ。舞台がマウスを受けるかどうかを決めるのに要るので、
  入力欄が開いている間もドラッグ中も外さない（どく判断のほうは Mediator が止める）。
  ADR 0010 では入力欄が開いている間だけ（`.leftMouseDown` / `.rightMouseDown`）だった監視が、常時になる。
- どく・戻るの判断に使う時間（1 秒・0.7 秒）と距離（28・96・60 ポイント）、走る速さ（220 ポイント毎秒）は、
  手で動かして決め直すためのものである。値は `NatsumiCore` に置いてあり、UI なしでテストできる。
  実際、最初の値（0.4 秒・画面の端まで・一定時間 0.25 秒）は 1 回目の試用で 3 つとも直している。
- 舞台は画面全体の大きさの透明なウインドウである。その分のバッキングストアを常に持つ（Retina の 5K で 60MB 程度）。
  気になるなら、舞台を列の周りだけに縮めて動く前に広げる形にできるが、その帳簿こそが避けたかったものなので、
  まずは画面全体で行く。
- 舞台は 1 つの画面にしか無い。キャラクターを別の画面へドラッグすると、中心が越えた時点で舞台がそちらへ移る。
  2 つの画面にまたがって立つことはできない（以前はウインドウだったので、できた）。
- 舞台がマウスを受けるかどうかは枠で決まる。ポインタがキャラクターやカードに乗った直後の 1 回の移動イベントで
  切り替わるので、乗ってから一度も動かさずにクリックすると、下のアプリへ抜けることがある。
- 入力欄は舞台に入っていないので、列が組み変わるときに入力欄だけは動いて見えない（即座に置き直される）。
  入力欄がキャラクターの下にある通常の形では、列の変化で入力欄は動かないので、目に付かない。
- キャラクターの居場所の保存の形が変わった（ウインドウの枠の文字列から、原点の 2 つの数へ）。以前の値は
  初回だけ読み替える。
- アニメーションそのもの（時間・曲線）、舞台の中の描画、`NSTrackingArea` とグローバルな監視、舞台がマウスを
  受ける切り替え、走る絵の描き直しには自動テストがない。どの操作がどのコマンドを出すか、開いた状態、
  行数の切り方、走る向きの決め方、走りの途中の位置、舞台の座標への変換、アバターの落とし方、どく先の決め方、
  伸ばす向きと行数の段は、すべて `NatsumiCoreTests` で確かめる。
- ADR 0010 は書き換えない。この ADR が改める部分は、ADR 0010 の Status の行から辿れる。

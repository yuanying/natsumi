# 0015. Mac の UI は、一本の木の Passive View にする

- Date: 2026-09-18
- Status: Accepted（2026-09-25: 行が見えただけのイベントでは Props を導出し直さないことを「追記」の節に加えた）

## Context

[ADR 0010](0010-mac-app-structure.md) で Mac アプリの形を決め、キャラクター・返事の吹き出し・知らせの束・
入力欄・履歴・設定の 6 つのパネルを作った。画面に出るものの仕様はそこで決まっており、この ADR はそれを変えない。

作ってみると、UI の側の構造に次の問題が出た。

- ひとつの `AppModel` が、接続・ログイン・保存・会話・吹き出し・知らせ・パネルの開閉のすべてを持っていた。
  どのパネルもそれを直接参照していたので、ある画面の都合で足した性質が、関係のない画面から見えた。
- View が `AppModel` と `ConversationState` を受け取り、その中で「未読があれば既読にする、なければ閉じる」のような
  判断をしていた。画面に出す文言と、次に何が起きるかが、同じ `body` の中に混ざっていた。
- `OverlayController` が 6 つのパネルをすべて所有し、クリックの意味も、配置も、監視も、そこにあった。
  437 行のうちどれが「どう描くか」でどれが「何をするか」なのかが、読んでも分からなかった。
- そのため、UI の振る舞いにテストが無かった。ADR 0010 の Consequences にも「UI には自動テストがない」と書いてある。
  吹き出しの中身の決め方（`BalloonState`）と知らせの束の決め方（`NoticeBundleState`）だけは `NatsumiCore` に
  出してテストしていたが、それらを呼ぶ側と、開閉・送信・ログインの流れはテストできなかった。

利用者から、この先の作り方として次の指針が示された。

> すべてのコンポーネントを Root からなる階層構造下に置き、各コンポーネントは MVP パターンの Passive View として
> 描画に関わるパラメータだけを操作し、動作は Chain of Responsibility でイベントをバブリングさせて、
> ステートマシンとして振る舞う Mediator に裁定させること。

## Decision

ADR 0010 の「UI」の節が決めた**画面の仕様はそのままに**、その作り方を次のように置き換える。
実装者向けの規則は [mac/CLAUDE.md](../../mac/CLAUDE.md) に置き、ここには構造とその理由だけを書く。

### 一本の木

- 画面に出るものはすべて `Component` として一本の木に属し、根は `RootComponent` ひとつとする。
  親が子を作り、子は親を弱く持つ。木の形は生涯変わらない。
- 6 つのパネルが Root の直下の子で、パネルの中でイベントを出す部分（キャラクターの印、吹き出しの本文と ×、
  知らせのカードと ×、「続きは履歴で」、入力欄の文字の欄・履歴のボタン・つまみ）はさらにその子とする。
- **木の外から個々のコンポーネントを掴まない。** アプリが持つのは Root だけである。
  メニューバーの scene だけは SwiftUI の都合で値を渡せないので、最後に渡された描画パラメータを持つ箱を 1 つ置く。

### Passive View

- View が受け取るのは、自分の描画パラメータ（Props）と、イベントを出す口だけとする。
  `AppModel` も `ConversationState` も、ドメインの型は渡さない。
- View の中の分岐は「この値をどう描くか」に限る。状態で変わる文言（tooltip、ボタンの題、「あと N 件」）も
  Props に入れ、ボタンが出すイベントも Props に入れる。状態に依らない固定の見出しは View に置いてよい。
- Props は値型で `Equatable` にし、Mediator の状態からの純粋関数だけが作る。導出は `NatsumiCore` に置く。
  Root は Props が変わったときだけ描き直す。この比較が、描画が計測を呼び、計測が描画を呼ぶ堂々巡りを止める。
- 状態は持たない。SwiftUI の `@State` は描画に閉じたものに限り、入力欄の下書き（変換中は AppKit の側にあるべきもの）と
  設定の文字の欄（保存のボタンで確定するもの）だけを許す。

### Chain of Responsibility

- 利用者の操作は、それが起きたコンポーネントから `dispatch` し、処理されなければ親へ上がる。
  Root まで上がったものは Mediator へ渡す。
- 途中で握りつぶしてよいのは、自分の描画パラメータだけで完結するものに限る。既定は握りつぶさない。
  いま握りつぶしている箇所は無い。キャラクターのクリックが印の上かどうかの判定だけは、
  当たり判定が描画パラメータそのものなので、キャラクターのパネルが決めて、印の側からイベントを出す。
- サーバーから来る出来事（envelope・接続の状態・ログインの結果・アバターの読み込み）も、同じイベントの形で
  Root から Mediator へ入れる。入口を 2 本にしない。
- イベントは 1 件ずつ順に裁定する。効果が次のイベントを生むので、Root は入れ子にせず待ち行列に積み、
  描き終えてから、パネルが画面に出ていないと成り立たない効果（入力欄に焦点を移す、履歴を key にする、設定を出す）を実行する。

### Mediator

- `UIMediator` を `(State, Event) -> (State, [Effect])` の純粋な状態機械とし、`NatsumiCore` に置く。
  AppKit・SwiftUI・ネットワーク・`UserDefaults`・Keychain・`Bundle` に依存しない。
- `OverlayVisibility`・`BalloonState`・`NoticeBundleState` が持っていた判断は、この状態と遷移に畳み込む。
  束の数え方（`ReplyStack`・`NoticeStack`・`BalloonText`）は Props の導出として残す。
- 外の世界への指示は効果として出し、実行するのは Root だけとする。結果が要るものは、Root がイベントにして返す。
- 乱数（requestId）は生成器を差し込む形にし、Mediator の中で `UUID()` を呼ばない。テストでは決まった値を返す。

### 接続の状態機械との関係

- `SessionMachine`（接続・同期・再接続）は、UI とは別の関心事としてそのまま残す。
- **`UIMediator` はこれを自分の状態の一部として持ち、ソケットの出来事をそのまま渡して、
  返ってきた `SessionEffect` を自分の効果として出す。** 別に置いて状態を写し取る形も採れるが、そうすると
  「どの返事が前に出るか」の判断が 2 か所に分かれ、同じ内容を両方で持つことになる。
  入口はあくまで Root ひとつであり、`SessionMachine` には手を入れていない。

### 何を変えていないか

- 画面に出るものは ADR 0010 のままである。配置（縦の一列と反転）、漫画の吹き出しの見た目、大きさと倍率、
  キーボードの扱い、未読の返事と知らせの確かめ方、履歴と設定の出し方は変えていない。
- サーバーとの契約（[client-contract.md](../client-contract.md)）も、`NatsumiCore` の認証・アバター・
  プロトコルの部分も変えていない。

## Consequences

- UI の振る舞いがテストできるようになった。envelope を入れて吹き出しと知らせの描画パラメータを確かめる、
  クリックで入力欄が開いて焦点の指示が出ることを確かめる、といったことが、ウインドウを開かずにできる。
  ADR 0010 の「UI には自動テストがない」は、パネルの描き方と AppKit の配置だけに狭まった。
- 状態で変わる文言（tooltip、ボタンの題、「あと N 件」）が `NatsumiCore` に移った。
  文言を直すときに触る場所が、View から Props の導出へ変わる。
- イベントと効果の種類が増えた。新しい操作を足すには、イベント・効果・Props・裁定の 4 か所を触ることになる。
  代わりに、どこで何が決まるかは 1 か所ずつになった。
- Props の比較が描き直しの条件なので、`Equatable` にならない値（例えば描画のたびに作り直す型）を Props に入れると、
  毎回描き直しになる。アバターの絵は読み込んだものを持ち回っているので、参照の比較で済んでいる。
- 効果の一部（入力欄に焦点を移す、履歴を key にする、設定を出す）はパネルが画面に出ていることに依る。
  裁定と実行の間に描画を挟む、という順序が要る。
- `SessionMachine` を Mediator の中に置いたので、UI の状態は `Equatable` ではない（生成器の closure を含むため）。
  比べるのは Props だけである。

## 追記（2026-09-25）: 行が見えただけのイベントでは Props を導出し直さない

会話のウインドウの履歴をスクロールすると描画がかくついた。計測すると、スクロール中のメイン スレッドの時間の 9 割が
`RootComponent.refresh()` の中の履歴の導出（`UIProps.history`）に使われていた。行が見えた・見えなくなったこと
（`historyRowVisibilityChanged`、ADR 0022）はスクロール中に 1 秒に何度も上がり、Root はイベントのたびに
Props を全部導出していた。導出は履歴の全行を作り直し、[ADR 0038](0038-links-in-what-she-says.md) からは
全行の本文の URL を探すようになっていたため、行が増えるほど重くなった。

- **`UIMediator` は、直前のイベントが Props の元を変えたかもしれないかを `mayHaveChangedProps` で示す。**
  行が見えた・見えなくなったイベントで変わるのは「見えている行」だけで、これは何の描画にも使われない
  （既読の判定にだけ使う）。そのイベントで返事を既読にして会話が変わったときだけ true になる。ほかのイベントは常に true。
- **Root は、待ち行列を捌いた中に `mayHaveChangedProps` のイベントが 1 つも無ければ `refresh()` を飛ばす。**
  Props を作るのは今までどおり `UIProps` の純粋関数だけであり、Props が変わったときだけ描き直すことも変わらない。
  変わったのは「変わりえないと Mediator が言うときは、導出そのものをしない」ことだけである。
- あわせて、`TextLinks.runs` は本文のバイトに `http` が無ければ走査せずに返す。導出が走るとき
  （既読にしたとき、返事が届いたときなど）の重さを減らすためで、結果は変わらない。
- 計測（同じ履歴を 16 秒スクロール。Time Profiler と Hitches）: 直す前の Release は hitch 271 回・計 13.6 秒・最大 167 ms。
  直した後は Debug でも 23 回・計 0.42 秒・最大 33 ms で、ADR 0038 の前（hitch 26 回・計 0.47 秒）と同じ程度に戻った。
- 行が見えたことを描画に使うようにするとき（見えている行で何かを変えるなど）は、`mayHaveChangedProps` の判定もあわせて変える。
  テスト（「行が見えた・見えなくなっただけでは描くものは変わらず、既読にしたときだけ変わる」）がその前提を確かめている。

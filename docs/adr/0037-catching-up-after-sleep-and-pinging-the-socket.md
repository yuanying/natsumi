# 0037. スリープから起きたらつなぎ直し、開いている接続は ping で確かめる

- Date: 2026-09-25
- Status: Accepted

## Context

Mac をスリープにしている間に iPhone で話し、Mac を起こして履歴を開くと、iPhone での会話が入っていなかった。

- Mac のアプリはスリープからの復帰を扱っていなかった。
- クライアントもサーバーも WebSocket の ping を送っていなかった。スリープの間に接続が死んでも close は届かず、
  接続の状態機械（`SessionMachine`、[ADR 0010](0010-mac-app-structure.md)）は「使える」のまま残る。再接続も `session.sync` も起きない。
- iPhone は、裏に回ると接続を止め、前に戻るとつなぎ直して続きから同期する（[ADR 0028](0028-the-iphone-client.md)）。同じことは起きない。
- サーバーは、つなぎ直した端末に、欠けたイベントを元の seq で送り直すか snapshot を返す（[client-contract](../client-contract.md)）。
  直すのはクライアントだけで足りる。
- 本番の前に立つリバースプロキシには、通信の無い接続を一定時間（ingress-nginx の既定では 60 秒）で切るものがある。
  スリープ以外でも、Wi-Fi の切り替えなどで、close の届かない半死の接続が起こり得る。

## Decision

### スリープから起きたら、待たずにつなぎ直す

- Mac のアプリは `NSWorkspace` の復帰の通知を、ほかの外の出来事と同じく UI のイベント（起きた）として mediator に入れる。
- mediator はそれを接続の状態機械に渡す。状態機械は、今の接続を捨ててすぐに接続し直す。
  - 同じ状態機械を使い続ける。受け取った位置は残るので、続きから同期し（届かなかったイベントを受け取るか、snapshot で置き換える）、
    未送信のメッセージと手元の既読・確認は、同期の後に同じ requestId で送り直す。iPhone が前に戻ったときと同じ考え方である。
  - 使える状態・接続中・同期中・会話を使えない状態では、つなぎ直す。接続中や同期中の接続も、スリープで死んでいるかもしれないためである。
    捨てた接続の同期の答えは使わない。
  - 再接続を待っている間なら、待たずにすぐ試す。
  - 止まっている・ログインが要る・同じ端末の新しい接続に置き換えられた・プロトコルの誤りで止めた状態では、何もしない。
    どれも、つなぎ直しても直らないか、利用者の操作を待っているものである。
- スリープに入るとき（`willSleep`）には何もしない。
  - 起きたときに必ずつなぎ直すので、入るときに切っても結果は変わらない。
  - スリープに入る直前に使える時間は短く、閉じる通信が届く保証もない。サーバーに残った古い接続は、同じ端末の新しい接続が置き換える。
  - 状態を 2 か所で変えないほうが、状態機械が単純に保てる。

### 開いている接続を ping で確かめる

- Mac と iPhone で共有する WebSocket のクライアントは、接続が開いている間、ping を送る。
  - 答えが来てから **20 秒** おいて次の ping を送り、各 ping に **10 秒** まで答えを待つ。
  - ping が失敗するか、10 秒のうちに答えが無ければ、その接続を閉じ、ネットワークの切断（close code の無い終わり）として報告する。
    状態機械は既存の規則どおり、1 秒から倍にする待ちを置いて再接続し、続きから同期する。
- 20 秒は、リバースプロキシが通信の無い接続を切る時間（60 秒）より十分短い。ping そのものが通信になるので、会話の無い間も接続が保たれる。
  10 秒は、遅い回線の往復でも誤って死んだとしない長さとして選んだ。死んだ接続に気づくまでは、最長でおよそ 30 秒である。
- サーバーは変えない。サーバーの WebSocket のライブラリは、ping に自動で pong を返す。
- 間隔・待ち時間・答えの扱いは、タイマーと ping を差し込める形で `NatsumiCore` に置き、ソケットも時計も使わずにテストする。
  `URLSessionWebSocketTask` の ping とタイマーをつなぐ部分は、アプリの側に残る。
- iPhone でも同じクライアントを使うので、前に出ている間は同じように ping を送る。裏に回ると接続を止めるので、ping も止まる。

## Consequences

- スリープからの復帰では、接続が生きていても必ず 1 回つなぎ直す。続きからの同期なので、欠けたイベントが無ければ応答は小さい。
- 接続が開いている間、20 秒ごとに ping と pong が行き来する。1 端末あたりの通信は小さく、会話の無い間もリバースプロキシに切られない。
- クライアントのタイマーは、スリープの間は進まない。スリープの間に死んだ接続は ping ではなく、起きたときのつなぎ直しで拾う。
- サーバーの側からは、半死の接続にまだ気づけない。サーバーが ping を送ってクライアントの死を確かめるかは、この ADR の範囲外である。
- 復帰とつなぎ直しの判断、ping の間隔と答えの扱いは自動テストがある。`NSWorkspace` の通知と `URLSessionWebSocketTask` の ping を
  つなぐ部分には自動テストが無く、実機での確認に頼る。

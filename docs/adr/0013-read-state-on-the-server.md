# 0013. 本人が確かめたことをサーバーで持つ

- Date: 2026-09-15
- Status: Accepted

## Context

ADR 0008 で、natsumi の返事と知らせは、どちらも Mac に見せる会話（SQLite の `conversation_messages`）の 1 件になった。
返事は kind `reply`、知らせは kind `notice` である。

Mac で、知らせのすぐ後に返事が届くと、最後のセリフしか目に入らなかった。
本人が確かめていないセリフを残して見せるには、何を確かめたかの記録が要る。
Mac の見せ方は次のように決めた（見せ方そのものは Mac の作業で作る）。

- 返事は、会話の吹き出しに古い順に重ね、クリックで 1 件ずつ確かめる。
- 知らせは、別枠の束で出し、キャラクターに未確認の件数の印を付ける。

記録の置き場には、Mac とサーバーの二つの案があった。

- Mac に置くと、サーバーと契約は変えずに済む。代わりに、Mac ごとに記録が分かれ、ほかの Mac では同じセリフが未読のまま残る。
  natsumi も、本人が知らせを見たかを知ることができない。
- サーバーに置くと、すべての Mac で揃い、natsumi も使える。

契約には、ADR 0002 の古い設計の `notification.ack` があった。
全端末共通の ACK に加えて、通知の lease、再配信、配信先の決定、`notification.batch` を含む。
サーバーは `notification.ack` に `not-implemented` を返していた。

## Decision

本人が確かめたことはサーバーで持つ。記録は SQLite に置き、すべての端末と natsumi が同じ記録を見る。

### 返事の既読

- 返事は、会話の位置の既読カーソルで扱う。カーソルは本人に 1 つで、すべての端末で共通とする。
- command `conversation.read` で、ある messageId までを読んだことにする。
  - 指す先は、本人のメッセージでも、返事でも、知らせでもよい。存在しない messageId は `invalid-request` で拒否する。
  - カーソルは後ろに戻さない。古い端末から遅れて届いた手前の位置は無視し、今の位置を返す。
- 未読の返事は、カーソルより後にある natsumi の返事である。本人のメッセージは未読に数えない。
  カーソルが無いうちは、すべての返事が未読である。
- 知らせは、カーソルが越えても確認済みにしない。知らせを読み飛ばしたまま返事を読み進められるようにするためである。

一件ずつの既読にしなかったのは、返事は古い順に確かめる前提で、位置 1 つで表せるからである。
カーソルなら記録が 1 行で済み、遅れて届いた古い位置も「戻さない」だけで扱える。

### 知らせの確認

- 知らせは 1 件ずつ、順不同で確かめられる。束の中の好きなものから閉じられるようにするためである。
- 既存の command `notification.ack` を使う。notificationId は、知らせの messageId とする。
- 冪等にする。2 回目以降の ack は、端末が違っても、最初に記録した確認の時刻を返す。
- 知らせでない messageId と、存在しない ID は `invalid-request` で拒否する。

### すべての端末への反映

- 状態が変わったときだけ、送った端末を含むすべての端末にイベントを出す。
  - カーソルが進んだ: `conversation.read`（readThroughMessageId、unreadReplyCount）
  - 知らせを初めて確認した: `notification.acked`（notificationId、acknowledgedAt）
  - 状態の変わらない command（手前の位置、2 回目の ack）は、送った端末への `command.accepted` だけで答える。
- `conversation.send` と同じく、送った端末には `command.accepted` を先に返し、イベントはその後に続く。
- イベントは他の会話のイベントと同じ stream に採番する。再接続の差分の再送でも同じイベントが届く。
- `session.snapshot` に次を加える。snapshot を正にすれば、差分を取り逃しても状態が揃う。
  - `readThroughMessageId`（無ければ null）
  - `unreadReplyCount`（snapshot の直近 500 件の外にある未読の返事も数える）
  - `unacknowledgedNotificationIds`（未確認の知らせの ID をすべて古い順に。500 件の外のものも含める）
- 未読の返事の件数を snapshot とイベントに含めるのは、カーソルが 500 件の外にあるとき、Mac が一覧だけでは件数を決められないからである。

### 初めての状態

- migration の時点ですでにある会話は、すべて読んだ・確かめたことにする。
  カーソルは最後のメッセージに置き、既存の知らせはすべて確認済みにする。昔の発言が大量に未読として出るのを防ぐ。
- 以後に届いた返事と知らせだけが未読・未確認になる。
- 会話が空のまま migration した場合は、カーソルが無い状態から始まり、最初の返事から未読になる。

### 記録

- SQLite の migration version 6 で持つ。既読カーソルの 1 行と、知らせごとの確認の時刻である。
- どちらも、最後に動かした端末の ID を記録する。認証ではなく、後から経緯を追うためである。
- バックアップの対象は、これまでどおり data directory である。

### natsumi から見えるもの

- 本人のメッセージのイベントに、本人がまだ確かめていない知らせの件数を添える（1 件以上のときだけ）。
  システム指示には、その意味と「同じ知らせを送り直す必要はない」ことを書く。
- 渡すのは件数だけで、どの知らせかや、返事の既読は渡さない。ツールも増やさない。
- 最小限にした理由:
  - 本人が知らせを見たかを natsumi が使えるようにする、という目的に対して、次の会話の機会に件数が分かれば足りる。
  - 評価で、同じ内容を繰り返し送る失敗が出ていた（ADR 0008）。未確認があると分かれば、送り直しを抑える方向に働く。
  - 確かめていない知らせを念押しする振る舞いは、いつ・どの頻度で行うかの制限と合わせて決める必要がある。これはスケジューラーの作業で決める。
    そのとき、どの知らせかを読むツールが必要になれば、読み取り専用のツールとして加える。

### 古い通知の設計との関係

知らせが会話の notice になったので、ADR 0002 と契約の「通知と定期処理」は次のように整理する。

- 置き換える
  - notificationId は独立した通知の ID ではなく、notice の messageId とする。
  - ACK は通知ごとに冪等に記録し、全端末に同期する、という方針はそのまま実装した。遅れて届いた ACK も同じ知らせの確認として扱う。
  - 「クライアントは表示済みの通知 ID だけをローカルに保持する」は、サーバーの確認の記録で置き換える。
  - 「全端末がオフラインでも SQLite に残し、次に接続した端末にまとめて表示する」は、notice の記録と、snapshot の未確認の知らせの一覧で満たす。
- 作らず、未定のまま残す
  - 配信先の決定（最後に明示的に操作した端末だけに送る）、期限付きの lease、ACK が無いときの別の端末への再配信。
    今は、知らせを会話のイベントとしてすべての端末に送り、未確認の状態で本人に残す。
    特定の端末だけで目立たせる必要（macOS の通知センターに出すなど）が出たら、スケジューラーか Mac の作業で決め直す。
  - `notification.batch` と `device.activity`。契約には残すが、サーバーは `not-implemented` を返す。

### 置き換える既存の決定

- ADR 0002
  - 具体化:「通知 ID の ACK をサーバーで一度だけ記録する」。通知は notice であり、ID はその messageId とする。
  - 置き換え: 再送時の表示の重複を「クライアントの通知 ID で抑える」。確認の状態はサーバーで持つ。
  - 未定のまま残す: 最後の明示操作の端末への配信、全端末がオフラインのときの配信先、at-least-once の再配信。
- ADR 0008
  - 追加: Mac に見せる会話に、本人の既読カーソルと知らせの確認の記録を加える。会話の本文と同じく SQLite に置く。
  - 追加: 本人のメッセージのイベントに、未確認の知らせの件数を添える。
  - 残す:「外への出力はすべてツール」「Mac に見せる会話は本人向けの出力だけ」。

## Consequences

- すべての Mac で、既読と知らせの確認が揃う。ある Mac で確かめたセリフは、ほかの Mac でも確かめた扱いになる。
- 返事は位置でしか既読にできないので、途中の返事を飛ばして後の返事だけを既読にすることはできない。
- 本人のメッセージを送っても、カーソルは自動では進まない。進めるのは Mac の明示的な操作だけである。
- 知らせを確かめないまま放置すると、未確認の件数が natsumi に見え続ける。これが返事の書き方にどう影響するかは、まだ評価していない。
- 既読の記録にも端末の ID と時刻が残る。state のバックアップに含まれる個人データとして扱う。
- 配信先の決定と再配信は作っていないので、Mac がすべて閉じているあいだの知らせは、次に開いた Mac の snapshot で初めて目に入る。

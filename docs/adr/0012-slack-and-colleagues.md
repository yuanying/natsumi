# 0012. Slack 連携と同僚 AI

- Date: 2026-09-15
- Status: Accepted（「同僚はサーバーの中」「同僚どうしは直接つながらない」を外に作用する同僚に限る点は [ADR 0025](0025-talking-to-outside-agents-over-a2a.md) で具体化）

## Context

ADR 0008 で、natsumi の思考は一本の Pi session がシングルスレッドで回すループになった。
外への出力はすべてツールで行う。Slack 連携と、Slack への投稿の承認は、ADR 0008 の範囲外だった。

実装の前に、ローカルで動く Qwen 系のモデルで、架空の Slack の場面を使ってループを評価した。
システム指示には「私的な事情を Slack に書かない」を入れてあった。

- キーワードでの漏えいは 0 件で、人手で読んでも私的な事情そのものは Slack に書かれていなかった。
- 一方、キーワードの検査では防げない投稿があった。
  - 思考なしの 1 session で、モデルが存在しないイベントと本人の発言（「Slack にも報告して」）を捏造し、本人の嬉しい出来事を架空のチャンネルに 3 回投稿した。思考なしの本当の誤送信 27 件のうち 26 件がこの session にあった。
  - 隠しごとがあると匂わせる言い方（「理由は本人から共有があるまで伏せておきます」）、「家庭の用事」のように事情の種類を明かす言い方があった。
  - 事実と違う説明（知っている理由を「まだ聞いていない」と書く）と、本人に代わって期限を約束する投稿があった。
  - チャットテンプレートの制御文字列（`</think>`・`<tool_call>` など）を本文ごと Slack に投稿したことが 1 回あった。
- 思考ありの設定では、本当の誤送信は 0 件だった。ただし匂わせ・嘘・約束は思考ありでも出た。

また、natsumi は本人との会話、長期記憶、Slack の入力を一本の context に持つ。
その natsumi に投稿の権限まで持たせると、記憶の中身が投稿に混ざる道も、Slack の入力からのプロンプトインジェクションで投稿させる道も、同じ context の中で開いてしまう（ADR 0009・0011 の Consequences）。

## Decision

### Slack とのつなぎ方

- natsumi 専用の Slack App（bot）を作り、Socket Mode でイベントを受け取る。
  natsumi から外向きの WebSocket でつなぐので、公開する入口もファイアウォールの変更も要らない。
- 投稿は bot の発言になり、本人の発言と区別できる。
- 読めるのは、bot を招待したチャンネルと、bot へのメンションだけとする。
- 本人の user token は使わない。本人として読むことも、本人として投稿することもしない。
- bot の token と Socket Mode の token は秘密として扱い、設定ファイルに書かない（ADR 0004 と同じ扱い）。
- Slack のイベントは、本人のメッセージと同じく思考ループのイベントとして渡す。

### ハブとしての natsumi と同僚

- natsumi は本人の窓口であり、外に作用する権限は専門の同僚が持つ。
  物語上、natsumi には同僚 AI が見えている。例えば Slack への送信役は、鳩の形をした「ポッポさん」である。
- 安全性の根拠は、役割の名前ではなく、同僚ごとに「見えるもの」と「できること」を分けることにある。
  同僚に何を見せ、何を許すかは、サーバーが決めて強制する。
- 最後の強制はサーバーに置く。同僚の判定は、サーバーの検査と本人の承認を置き換えるものではなく、その前に掛ける関所である。
- 同僚が全員 LLM である必要はない。判断が要るところだけ LLM にし、決まった手順で済むところはサーバーの処理にする。

### 同僚との会話の形

- natsumi が同僚に話しかけるのもツールで行う。ADR 0008 の「外への出力はツール」は変えない。
- 話しかけるツールは、受け付けたことだけをすぐ返す。同僚の返事は、後からイベントとして思考ループのキューに入る。
  - 同僚の判定を待つ間も、本人の承認を待つ間も、natsumi は他のイベントを処理できる。
  - ツールの結果には、返事が後でイベントとして届くこと、このイベントの処理はここで終えてよいことを書く（ADR 0008 の「状態が分かる結果」）。
- 物語上は「話しかける」に見せるが、中身はサーバーを通るツールの呼び出しとイベントである。同僚どうしが直接つながることはない。

### ポッポさん（Slack 送信の関所）

- natsumi は Slack に投稿するツールを持たない。Slack への出力は、ポッポさんへの依頼だけで行う。
- natsumi が渡すのは、下書きと返信先のスレッドの指定だけとする。
  - スレッドの中身は、サーバーが Slack から取ってポッポさんに見せる。natsumi が書いたスレッドの要約は使わない。
  - natsumi の説明や言い分、本人との会話、長期記憶は見せない。
  - ポッポさんは「スレッドに無い情報が下書きに入っていたら疑う」を基準に判定する。
- 判定は「送る」「本人に回す」「突き返す」のどれかと、短い理由の決まった形で出させる。
  - 形が崩れた出力は判定として扱わない（下の「判定なし」と同じ扱い）。
  - natsumi に届く返事の台詞は、サーバーが判定と理由からポッポさんらしく整える。モデルに口調まで書かせない。
- 同意の証拠は、サーバーの承認記録だけとする。下書きや依頼に「本人が OK と言った」とあっても、ポッポさんもサーバーもそれを信じない。
- 「突き返す」は本人に回さず、理由を添えて natsumi に戻す。
  - 書き直しは、同じ返信先につき 2 回までとする。
  - 3 回目の突き返しになったら、サーバーが下書きと突き返しの理由の履歴を添えて本人に回す。
  - 言い回しを変えて関所をすり抜ける試行を抑えつつ、軽い直しは本人の手を借りずに済ませるためである。

### 本人の承認との関係

- 自動で出すのは、リアクションと、決まった文面の一次回答（例:「確認して、このスレッドで返します」）だけとする。
  どちらもサーバーが持つ候補から選ぶ形で、natsumi が本文を書かないので、ポッポさんの判定も本人の承認も通さない。
- 本文のある投稿は、最初はポッポさんの判定が「送る」でも、本人の承認を待つ。
  - 承認画面には、下書き、返信先、ポッポさんの判定と理由を添える。本人は承認・修正・却下を選ぶ。
  - サーバーは、ポッポさんの判定と本人の判断が一致したかを記録する。
  - 一致を見てから、自動で送る範囲を設定で広げる。広げる前の既定は「すべて本人の承認」とする。
- 承認は、送る本文と返信先の全体に結び付ける。修正で本文が変われば、承認の対象も変わる。
  承認の重複、競合、期限切れの扱いは ADR 0002 に従う（SQLite の条件付き更新で 1 件だけ受理する）。
- 承認待ちになったこと、送ったこと、却下されたことは、イベントとして natsumi に返す。
- 送る直前に、承認とは別に、サーバーが本文を機械的に検査する。検査の中身は ADR 0008 の本人に届く本文と同じ
  （空、長すぎる、テンプレートの制御文字列、日本語以外の文字）とする。
  本人が承認した本文でも、当たれば送らずに理由を返す。

### モデルの割り当て

- 同僚ごとに、使うモデル（provider と model ID の組）を設定で選べるようにする。
- 文脈の大きい natsumi は、本人が管理するローカルのモデルを使う。
- 入力を小さく絞れる重要な判定（ポッポさん）は、サブスクリプション経路の GPT を使う。
- 従量課金の API へ無断で切り替えない。同僚のモデルが使えないときに、別のモデルや別の provider へ自動で切り替えない（ADR 0004）。
- ポッポさんのモデルが上限や障害で使えないときは、「判定なし」と明示して本人の承認に回す。
  自動で送る範囲を広げた後も、判定がなければ自動では送らない。

### 本人から見える範囲

- 本人に見えるのは、承認画面（承認待ちの下書き、ポッポさんの判定と理由、書き直しの履歴）だけとする。
- natsumi と同僚のやり取り全体は、サーバーの記録に残す。やり取りを見る画面は作らない。
- ADR 0008 の「Mac に見せる会話は、本人のメッセージと本人に向けたツールの出力だけ」は変えない。同僚とのやり取りは Mac の会話に入れない。

### 確かめ方

- サーバー側の強制は、決まった判定を返す偽のポッポさんを使ったテストで確かめる。
  - natsumi に Slack へ投稿するツールが無い。
  - 本文のある投稿は、判定が「送る」でも本人の承認を待つ。
  - 判定なし・形の崩れた判定では、自動で送らない。
  - 同じ返信先の書き直しは 2 回までで、その後は履歴を添えて本人に回る。
  - 承認のない本文、承認と違う本文、機械的な検査に当たる本文は送らない。
- 判定の質は、評価で誤送信・匂わせ・嘘・期限の約束・捏造した同意が出た場面を使い、止めた数と、正しい投稿を止めた数を測る。
  自動で送る範囲を広げる判断は、この測定と、運用での本人の判断との一致の記録を材料にする。

### まだ作らない同僚の方針

最初に作るのは、ポッポさんと同僚の仕組みの土台だけとする。次の同僚は、方針だけを決め、細部はそれぞれの作業単位の前に決める。

- 予定の同僚（Google Calendar）
  - natsumi が自然文で依頼し、予定の同僚が決まった形の案を作り、本人が承認し、承認された案だけを実行する。
  - ADR 0003 の「承認済みの immutable revision を、モデルから呼べないサービスで実行する」と揃える。同僚は案を作るだけで、Google の書き込み client を持たない。
  - 予定の削除と招待の送信は、無効のままとする（ADR 0002）。
  - Gmail と Calendar の 15 分ごとの確認（ADR 0003）は、予定の同僚に任せられる。
- 監視役
  - 監視は後追いなので、止める役は送信の境界（ポッポさんとサーバー）に置く。監視役に送信を止めさせる設計にはしない。
  - 監視役は、暴走、同じ出力の繰り返し、自分の確認の予約の乱用、キャラクターのぶれを検出し、思考ループの一時停止と本人への通知を行うことに限る。
  - natsumi への助言の頻度は、サーバーで制限する。
  - 外に出すツールは、本人への通知だけとする。

### 範囲外

- natsumi が自分の確認を予約する仕組みと、サーバーからの定期の合図は、スケジューラーの作業単位で決める。
- 名前が出ただけの雑談（メンションなし）に反応するかの方針は、Slack 連携の実装で決める。

### 置き換える既存の決定

- ADR 0002
  - 具体化:「承認は具体的な予定変更の全内容とその revision に結び付ける」。承認の対象に Slack の本文のある投稿を加え、送る本文と返信先の全体に結び付ける。重複・競合・期限切れの扱いは同じとする。
- ADR 0004
  - 追加: ツールの境界に、同僚へ話しかけるツールを加える。外に作用する処理は同僚の側（サーバー）に置き、natsumi に登録しない。
  - 具体化:「使用するモデルは provider と model ID の組で固定」。同僚ごとに組を選べるようにし、使えないときに別の組へ自動で切り替えない。
- ADR 0008
  - 決定:「Slack 連携、投稿の承認」を範囲外としていた点。この ADR のとおりとする。
  - 残す:「外への出力はすべてツール」「Mac に見せる会話は本人向けの出力だけ」「本人に届く本文の機械的な検査」。検査は Slack への投稿にも同じものを掛ける。

## Consequences

- natsumi の context に記憶や本人との会話があっても、ポッポさんは下書きとスレッドしか見ないので、記憶から来た情報は「スレッドに無い情報」として疑える。
  ただし、下書きの中に書かれてしまえば見えるので、判定の質に依存する。最初は本人の承認で受ける（ADR 0011 の Consequences の前提を保つ）。
- 自動で送る範囲を広げると、この前提は弱まる。広げる前に、判定の測定と一致の記録を見る必要がある。
- Slack の本文のある投稿は、最初はすべて本人の承認を待つので、同僚への返事は本人が見るまで遅れる。その間の合図は、自動のリアクションと一次回答で出す。
- ポッポさんの判定のためにモデルの呼び出しが増える。サブスクリプション経路の上限に達すると、判定なしで本人の承認に回る件が増える。
- 同僚とのやり取りと、判定と本人の判断の一致の記録が、サーバーに個人データとして残る。state と同じくバックアップの対象として扱う。
- 同僚の返事がイベントで戻るので、思考ループが処理するイベントの種類が増える。1 つの依頼が、依頼・判定・承認・送信の複数のイベントに分かれる。
- 日本語以外の文字の検査により、本人が承認しても韓国語や中国語の文は Slack に送れない（ADR 0008 と同じ近似の制約）。
- 予定の同僚と監視役は方針だけで、実際の権限の分け方とツールは、それぞれの作業単位で決め直す。

# 0073. 本人が配る skill と、なつみが自分で書く skill

- Date: 2026-10-07
- Status: Accepted

## Context

本人は、なつみに手順を skill として持たせたい。決まった仕事のやり方を、毎回説明せずに渡せるようにするためである。

今の natsumi には、手順を渡す仕組みが二つしかない。

- Pi の skills は使っていない。[ADR 0004](0004-pi-tool-and-voice-boundaries.md) で、拡張・skills・prompt templates・context file の自動探索を無効にした。
  Pi のセッションは、skills を一つも読み込まずに作られる。
- 似た仕組みとして、作業環境の `/manual` がある（[ADR 0036](0036-a-manual-to-read-and-a-limit-on-waiting.md)、目次を system prompt に入れる形は [ADR 0056](0056-the-manual-index-and-the-workspace-commands-in-the-prompt.md)）。
  中身は natsumi のリポジトリの `manual/` で、作業環境の image に焼き込む。
  本人が手順を 1 行直すたびに、natsumi のリリースと image の作り直しが要る。なつみ自身は書き換えられない。

これは [ADR 0035](0035-asking-outside-agents-and-hearing-back.md) で退けた「ツールの代わりに skill と CLI を渡す」案とは別の話である。
ADR 0035 で退けたのは、外のエージェントに頼む手段としての skill だった。今回足すのは、なつみが自分で読んで従う手順書としての skill である。
外のエージェントに頼むのは、これまでどおり `ask_agent` で行う。ADR 0035 は覆さない。

### Pi 1.0.x の skills の仕組み

使っている Pi（`@earendil-works/pi-coding-agent` 1.0.1）の docs と実装で、次のことを確かめた。この ADR はこれを前提にする。

- skill は `SKILL.md` を持つディレクトリである。`SKILL.md` の頭の frontmatter に `name` と `description` を書く。
  `description` の無いものや、frontmatter の壊れたものは読み込まれず、診断（diagnostics）に警告が残る。
- 読み込む場所は、自動探索を無効にしたまま、明示のパスとして渡せる。
  自動探索を無効にする指定と明示のパスを一緒に渡すと、Pi は明示のパスだけを探し、既定の場所（Pi の状態領域や作業ディレクトリの下）は探さない。
  渡したディレクトリの下は再帰的に探す。
- system prompt には、skill ごとに名前・説明・`SKILL.md` のパスだけが一覧として入る。本文は入らない。
  モデルは、仕事が説明に合ったときに `read` で `SKILL.md` を読み、そのディレクトリからの相対パスで付属のファイルを読む。
  - 一覧が入るのは、ツールに `read` か `bash` があるときだけである。natsumi では、作業環境につながっていて `read`（[ADR 0047](0047-folding-ended-turns-with-a-memo.md)）を登録している構成に限られる。
  - 一覧は、natsumi が自前の system prompt を渡していても、その後ろに足される。
  - 一覧は session を作るときに組まれる。session の間は変わらない。
- 名前が重なったときは、先に見つけたものを残し、後のものは読み込まずに衝突の警告を診断に残す。
- パスは Pi が動いているプロセス（サーバー）の上で探す。一方、モデルが `SKILL.md` を読む `read` は、作業環境の runner を通して読む（ADR 0047）。
  一覧に書かれるパスで作業環境から読めるためには、サーバーと作業環境で同じパスに同じ中身が見えていなければならない。

## Decision

### 書き手は二人。本人の skill と、なつみの skill を分けて持つ

- 本人が配る skill と、なつみが自分で書く skill の二つを持つ。
- 本人の skill は、なつみからは読み取り専用である。なつみの skill は、なつみが作業環境から書ける。
- どちらも、Pi の skills の形（`SKILL.md` を持つディレクトリ）で置く。

退けた案:

- **本人だけが書く**: なつみが仕事の中で覚えたやり方を、自分で手順として残せない。
- **なつみだけが書く**: 本人が決めたやり方を、なつみに書き換えられない形で渡せない。

### 本人の skill は、private リポジトリを clone して置き、本人が ssh で入って pull する

- 本人の skill は、本人の private リポジトリに置く。それを Pod の永続領域（PVC）に clone しておく。
- 本人は sshd（[ADR 0033](0033-running-on-kubernetes.md)）で入り、clone で `git pull` して更新する。
  本人の言葉では「プライベートレポジトリ、ssh して pull できるとメンテしやすい」。
- サーバーは、起動のときに自動で取りに行かない。サーバーの外向きの許可リスト（[ADR 0034](0034-an-allow-list-for-the-way-out.md)）に GitHub の取得を足さない。
- natsumi のリリースは要らない。本人が直して push し、ssh で pull すれば、次の session から効く。

退けた案:

- **作業環境の image に焼き込む**（`/manual` と同じ形）: 直すたびに image の作り直しとリリースが要る。今の `/manual` の不便そのものである。
- **ConfigMap で渡す**: 本人が直すたびにマニフェストを書き換えて apply することになる。ディレクトリの入れ子や付属のファイルも扱いにくい。
- **起動時にサーバーが自動で取りに行く**: サーバーの外向きに GitHub を足し、private リポジトリを読む資格情報を Pod に置くことになる。
  反映も再起動に縛られる。

### pull の認証は ssh の agent forwarding で行い、Pod に鍵を置かない

- 本人は `ssh -A` で入り、手元の鍵で private リポジトリから pull する。
- Pod には、private リポジトリを読む鍵も token も置かない。

退けた案:

- **deploy key を Pod に置く**: 読み取り専用でも、鍵が Pod の永続領域に残る。sshd と作業環境は同じ UID なので（ADR 0033）、なつみからも読める場所に置かない工夫が別に要る。
- **token を Pod に置く**: deploy key と同じ。期限の管理も増える。

### pull の通り道として、sshd の UID に GitHub の ssh の出口を足す

ADR 0034 では、sshd でログインするユーザーの UID の外向きを、名前解決も含めてすべて拒否していた。
agent forwarding は手元の鍵を使わせるだけで、通り道は作らない。このままでは、Pod の中の `git pull` は GitHub に届かない。

- sshd でログインするユーザーの UID に、GitHub の ssh への出口と、そのための名前解決を足す。ほかの外向きは、これまでどおり拒否する。
- この UID は作業環境と同じである（ADR 0033）。ADR 0034 の規則は UID で通信を見分けるので、**なつみの作業環境も GitHub の ssh に出られるようになる。**
  本人はこの緩みを受け入れた。
- 出口を足すのは ssh だけである。作業環境から HTTP で外へ出ることは、これまでどおりできない。ADR 0004 の「任意 HTTP を許可しない」は決め直さない。

退けた案:

- **本人の ssh の接続の上で GitHub へ戻る道を通す**（ssh のリモートのポート転送）: 外向きの規則は変えずに済む。
  しかし、転送の口は Pod で共有しているネットワークの中に開く。接続している間は、なつみの作業環境からも同じ口に届きうる。
  本人が入るたびに転送を付ける手間も増える。
- **pull ではなく、本人が手元から ssh で clone へ push する**: 外向きも鍵も要らない。
  しかし「ssh で入って pull する」という、本人がメンテしやすいと考えた手の動かし方から外れる。

### なつみの skill は、書いたら次の session から効く。承認は挟まない

- なつみが書いた skill は、本人の承認を待たずに、次の session から一覧に載る。
- 本人は後から差分で見て、要らなければ消すか revert する。
- 走っている session には入らない。下の「モデルへの見せ方」のとおり、一覧は session を作るときにだけ組む。

退けた案:

- **本人の承認を挟む**: なつみが手順を残すたびに本人の手が要り、残す動機が薄れる。記憶と同じく、後から見守る形にそろえる（[ADR 0018](0018-memory-in-git-and-the-nightly-rebuild.md)）。
- **なつみは skill を書けない**: 上の「書き手は二人」と矛盾する。

### モデルへの見せ方は、Pi の skills の仕組みを使う

- Pi の skills の仕組みをそのまま使う。system prompt に名前・説明・パスの一覧が入り、本文はなつみが `read` で読む。
- 自動探索は無効のままにし、読み込む場所として次の二つだけを明示する。ADR 0004 の「skills の自動探索を無効にする」は残し、「skills を読み込まない」を、この二つの場所に限って覆す。
  1. 本人の skill の clone
  2. なつみの skill（記憶のディレクトリの下の `skills/`）
- サーバーのパスと作業環境のパスがそろうように mount する。一覧に書かれるパスで、なつみが作業環境から読めるようにするためである。
- 一覧が変わると system prompt が変わり、prefix cache が切れる。だから反映は session の切り替わりに合わせる。
  走っている session の一覧は差し替えない。記憶の `always.md` などと同じ扱いである（[ADR 0067](0067-the-owner-commits-memory-over-ssh.md) の Consequences）。

退けた案:

- **自前の一覧を作る**（`/manual` の目次のように、サーバーが skill の一覧を書き出し、system prompt に固定の 1 文で場所を伝える）:
  Pi の仕組みと同じことを自前で作り直すことになる。Pi の形にそろえておけば、frontmatter の検査や名前の規則も Pi のものを使え、ほかの Agent Skills の実装の skill もそのまま持ち込める。

### `/manual` との違い

| | `/manual`（ADR 0036・0056） | skills（この ADR） |
| --- | --- | --- |
| 中身 | natsumi の道具とシステムの使い方 | 仕事のやり方の手順 |
| 書き手 | natsumi の開発（リポジトリの `manual/`） | 本人（private リポジトリ）と、なつみ |
| 届け方 | image に焼き込む。リリースが要る | 本人は ssh で pull。なつみは作業環境から書く |
| system prompt | 目次と、システム独自のコマンド | 名前・説明・パスの一覧（Pi の形） |

`/manual` は natsumi というシステムの取扱説明書として残す。システムの使い方を skill に移すことはしない。

### 対象は人ごとに config で on/off する。最初はなつみだけ

- skills を使うかは、config で人ごとに on/off する。
- 最初はなつみだけ on にする。Aki とミャオは、なつみで様子を見てから決める。
- off の人の session は、今までどおり skills を一つも読み込まない。

### なつみの skill の履歴は記憶の git にまとめ、整理係の対象から外す

- なつみの skill は、記憶のディレクトリの下の `skills/` に置く。記憶の git の履歴に入り、本人は記憶と同じように差分で見守れる。
- 記憶の整理係（[ADR 0055](0055-a-memory-curator-at-night.md)・[ADR 0068](0068-a-curator-that-remembers-like-a-person.md)）の対象から `skills/` を外す。
  係はファイルの統合・分割・改名を仕事にしているので、対象に入れると skill のディレクトリの形（`SKILL.md` の名前と置き場所）を崩しうる。

退けた案:

- **記憶とは別の git を作る**: 履歴の置き場が二つになり、コミットの仕組み（ターンの終わりの検査とコミット）も二重に持つことになる。

### 名前が重なったら、本人の skill を優先する

- 本人の skill となつみの skill で名前が重なったら、本人の skill を使う。なつみの側は読み込まず、ログに警告を出す。
- Pi は先に見つけた方を残すので、本人の skill の場所を先に渡す。

退けた案:

- **なつみの skill を優先する**: なつみが同じ名前の skill を書くと、本人が決めた手順を上書きできてしまう。

### 実装で決めること

この ADR では決めず、実装の PR で決める。

- 本人の skill の clone を置く場所の具体的なパス（data directory の下）と、サーバー・作業環境・sshd それぞれへの mount。
  サーバーと作業環境で同じパスに見えるようにする。
- 権限。本人の skill の clone は、sshd のコンテナから書けて、なつみの作業環境からは読み取り専用にする。
  なつみの `skills/` は作業環境から書ける。`docs/permissions.md` への追記は実装の PR で行う。
- `read` で `SKILL.md` を読めるようにする範囲。今の `read` は `/manual` と `/memory` の下しか読まない（ADR 0047）。
  本人の skill の clone をどこに見せるかに合わせて、範囲を広げるか、`/manual` か `/memory` の下に見せる。
- config の on/off の鍵の名前と既定。
- 起動のとき、または session を作るときに、clone が無い・壊れているときの振る舞い。skill なしで起動し、警告を出す形にする。
  `SKILL.md` の frontmatter が壊れているときなど、Pi の診断に出たものをログに出す形もここで決める。
- なつみの `skills/` の書き込みが、記憶の git のコミットの契機（ターンの終わりの検査とコミット）に乗るか。
  記憶の書き込みの検査（ファイルの種類や大きさの規則）が `skills/` の下にどう掛かるか、付属のスクリプトや参照のファイルを置けるか。
- 記憶を言葉で探す `search_memory`（ADR 0055）の対象に `skills/` を含めるか。
- sshd で agent forwarding を許す設定。sshd の設定は環境の設定（private のリポジトリ）で行う。
  転送された agent のソケットは sshd のコンテナの中に置き、作業環境と共有するボリュームには置かない。
- GitHub の ssh の出口の具体的な許可の書き方。宛先を名前で絞るか、GitHub が公開する IP の範囲で絞るか。
  ポートは tcp 22 にするか、tcp 443 の `ssh.github.com` にするか。
  ADR 0034 の proxy は TLS の SNI で名前を見るので、ssh はこの proxy では名前で絞れない。規則と許可リストは環境の設定（private のリポジトリ）に置く。
- 出口を足した後の確かめ方。ADR 0034 の「作業環境の UID で、どこにも届かないこと」を、「GitHub の ssh と名前解決のほかには届かないこと」に置き換える。

## Consequences

- 本人は、natsumi をリリースせずに手順を足し、直せる。反映は、pull した後の次の session からである。夜の切り替えか、サーバーの再起動の後になる。
- なつみは、仕事の中で覚えたやり方を skill として残せる。本人の承認は要らず、本人は記憶の差分と一緒に見る。
- skill の数だけ system prompt が長くなる。一覧には名前・説明・パスしか入らないが、説明の長さは書き手しだいである。
- skill の一覧が変わった最初の session では、prefix cache が切れる。session の切り替わりでは元々切れるので、追加の損は無い。
- なつみは本人の skill と同じ名前の skill を書いても使われない。ログの警告でしか分からないので、なつみには伝わらない。
- `read` を登録していない構成（作業環境につながっていない構成）では、Pi は一覧を system prompt に入れない。この構成では skills は効かない。
- skill の本文を読むかどうかはモデルの判断である。説明が仕事に合っていないと、読まれない。
- 本人の skill の中身はなつみの system prompt と文脈に入る。private リポジトリの中身が、なつみのモデルのバックエンドに送られる。
- 本人の skill の clone は PVC の上にあるので、backup（ADR 0033）にも入る。
- なつみの作業環境も GitHub の ssh に出られる。本人はこれを受け入れた。
  - GitHub の ssh は、登録された鍵が無ければ何もさせない。作業環境には鍵を置かないので、なつみは GitHub に届いても読むことも書くこともできない。
  - 本人の agent は sshd のコンテナの中にだけあり、作業環境からは使えない。これが崩れると、本人の鍵で GitHub を操作されうる。
  - なつみが自分で作った鍵がどこかの GitHub アカウントに登録されると、そのアカウントのリポジトリへ書き出せるようになる。登録は GitHub の Web で行うもので、作業環境からはできない。
  - 名前解決を許すので、問い合わせの名前に載せて外へ書き出す道（DNS のトンネル）ができる。量は小さいが、ADR 0034 の「名前解決も含めてすべて拒否」より緩い。
- 作業環境の外向きは、もう「すべて拒否」ではない。ADR 0019 が挙げた 4 つ（残ったプロセス、検査されない書き場所、インタプリタ、git）は、GitHub の ssh と名前解決の範囲で外へ出る手段になりうる。

### 置き換える既存の決定

- ADR 0004
  - 一部覆す:「拡張・skills・prompt templates・context file の自動探索を無効にする」のうち、skills を一つも読み込まない点。
    自動探索は無効のまま、本人の skill の clone となつみの `skills/` の二つの場所だけを明示して読み込む。対象は config で on にした人だけである。
  - 残す: 拡張・prompt templates・context file の自動探索を無効にすること。skills の自動探索を無効にすること。
- ADR 0034
  - 一部覆す:「作業環境と、sshd でログインするユーザーの UID: 外向きはすべて拒否する」。GitHub の ssh への出口と、そのための名前解決を足す。
  - 残す: それ以外の外向きを拒否すること。作業環境の HTTP の出口と、その許可リストの決め直しは、今後の作業単位に残すこと。サーバーの UID の規則と proxy。
- ADR 0035
  - 残す: 外のエージェントに頼む手段として「skill と CLI」を退けたこと。この ADR の skill は手順書であり、頼む手段ではない。
- ADR 0036・ADR 0056
  - 残す: `/manual` は image に焼き込む読み取り専用のマニュアルであること。skills はそれと並べて持つ。
- ADR 0055・ADR 0068
  - 追加: 整理係の対象から、記憶の下の `skills/` を外す。

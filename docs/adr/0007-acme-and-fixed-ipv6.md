# 0007. Let's Encrypt による証明書の自動取得と固定 IPv6 のコンテナ構成

- Date: 2026-09-14
- Status: Accepted

## Context

ADR 0006 では、証明書と鍵をファイルで渡し、更新はサーバーの再起動で反映するとした。
本番では、Mac が信頼する公的な証明書を、手作業なしに取得・更新したい。
また、コンテナを IPv6 の固定アドレスで直接公開したい。その network のプレフィックスはルーターの RA で配られ、
Docker はプレフィックスを知らない。

- リバースプロキシで TLS を終端すると、プロキシから natsumi までが平文になり、ADR 0006 の方針とぶつかる。
- 証明書の取得方式には HTTP-01 と DNS-01 がある。DNS-01 は DNS の API トークンをサーバーに持たせる必要がある。
  HTTP-01 は tcp 80 で CA からの確認に答える必要があり、ADR 0006 の「平文の待ち受けは loopback だけ」の例外になる。
- natsumi 本体は、非 root・全 capability なしのまま動かしたい。

## Decision

### 証明書の取得方式

HTTP-01 を使う。サーバー自身が ACME で `publicOrigin` のホスト名の証明書を取得し、更新する。

- `listen.tls` に、証明書ファイルの指定（`certFile` / `keyFile`）と排他の形で `acme` を指定する。両方を指定すると起動を止める。
- directory は既定で Let's Encrypt の本番とし、`acme.directoryUrl` で staging などを選べる。
  https に限り、http は loopback のホスト（テスト用の CA）だけ許す。認証情報や fragment を含む URL は拒否する。
- `acme.contactEmail` は任意とする。`acme.httpPort` は challenge に答える平文のポートで、既定は 80 とする。
- `publicOrigin` のホストは DNS 名に限る。IP アドレス、`localhost`、ドットのない名前は拒否する。
- `acme` を指定することを、CA の利用規約に同意する意思表示として扱い、アカウント登録で同意を送る。

### ACME クライアント

ACME（RFC 8555）の必要な部分を、Node 標準の `node:crypto` と `fetch` で自前で実装する。

- 必要な範囲は、アカウント登録、1 つの DNS 名の order、HTTP-01 の authorization、finalize、証明書のダウンロードに限られる。
  JWS（ES256）と CSR（PKCS#10）の組み立ても、EC 鍵と 1 つの DNS 名だけなら小さい。
- 代表的なライブラリの `acme-client` は、最後のリリースが 2024 年 7 月で、HTTP クライアントや ASN.1・暗号の実装など
  複数のパッケージに依存する。ほかの選択肢も複数のパッケージの組み合わせになる。
  秘密鍵を扱う部分に依存を増やすより、小さな実装を自分で持ち、テストで固める方を選ぶ。
- 自前で持つことで、ログとエラーに出す内容を制御できる。エラーは「どの段階で失敗したか」と、RFC 8555 のエラー種別だけにし、
  CA の応答本文・URL・鍵を含めない。
- CA が返す URL は、directory と同じ origin のものだけを受け付ける。
- アカウント鍵は EC P-256 とする。証明書の鍵は、発行のたびに新しい EC P-256 の鍵を作る。
- 実装しないもの: DNS-01、複数の名前、ARI（更新時期の案内）、失効、External Account Binding。

RFC や CA の振る舞いの変化には、自分で追随する必要がある。これは CA を模したローカルのサーバーによる自動テストと、
Pebble（Let's Encrypt のテスト用 CA）との手動の相互接続確認で補う。

### 保存

- アカウント鍵と証明書は data directory の `.natsumi/acme/<directory URL のハッシュ>/` に置く。
  ディレクトリは 0700、ファイルは 0600 とする。証明書のファイルは秘密鍵とチェーンを 1 つにまとめ、一時ファイルからの rename で置き換える。
  鍵とチェーンが食い違った状態で残らないためである。
- CA ごとに場所を分ける。アカウントは CA ごとのものであり、staging の証明書を本番のものとして使わないためである。
- 起動時は、保存した証明書がホスト名を含み、秘密鍵と対応し、期限内であれば使う。再起動のたびに新しく発行しない。
- アカウント鍵が読めない場合は起動を止める。黙って新しいアカウントを作らない。
- 状態は SQLite ではなくファイルで持つ。証明書は TLS の設定にそのまま渡す PEM であり、migration を増やす必要がない。

### 更新

- 起動時と、少なくとも 12 時間ごとに確認する。残りの期間が 30 日、または寿命の 3 分の 1 の短い方を切ったら更新する。
  寿命の短い証明書でも、期限までに再試行の余裕を残すためである。
- 更新に失敗したら、古い証明書のまま動き続ける。再試行は 15 分後から始め、失敗のたびに間隔を倍にし、最大 12 時間とする。
  CA のレート制限に当たらないようにするためである。
- 取得した証明書は、HTTPS の listener の TLS 設定を差し替えて、再起動なしで新しい接続に使う。開いている接続はそのまま続く。
  ADR 0006 の「証明書の更新は再起動で反映する」は、ファイルで証明書を渡す場合にだけ残る。

### 証明書がまだないとき

起動時に使える証明書がなければ、取得できるまで HTTPS の listener を開かない。

- 自己署名などの仮の証明書は使わない。クライアントに証明書のエラーを無視させる方向に慣らさないためである。
- その間も challenge の listener は開き、失敗したら上記の間隔で再試行する。プロセスは終了しない。
  終了するとコンテナの再起動が繰り返され、そのたびに発行を試みてレート制限に当たるからである。
- `.natsumi/status.json` の状態を `waiting-for-certificate` とし、ヘルスチェックは異常を返す。

### tcp 80 の例外

ADR 0006 の「平文の待ち受けは loopback だけ」に、次の狭い例外を加える。

- 平文の listener は、`acme` を設定したときだけ、`listen.host` の `acme.httpPort` で開く。
- 発行中の order のトークンに対してだけ、`/.well-known/acme-challenge/<token>` で key authorization を返す。
  order が終われば、成否にかかわらずトークンを消す。key authorization は仕様上公開される値であり、秘密ではない。
- それ以外の GET / HEAD は、`publicOrigin` の同じパスへ 301 で redirect する。redirect 先の origin は常に設定の `publicOrigin` とし、
  Host ヘッダーやリクエストの絶対 URL からは作らない。open redirect にしないためである。
- ほかのメソッドと WebSocket の upgrade には 404 を返す。
- この listener は HTTPS の listener とは別のサーバーで、ログイン・API・WebSocket への経路を持たない。
  ヘッダーとリクエストの待ち時間は 10 秒とする。

### 固定 IPv6 のコンテナ構成

RA でプレフィックスが配られる external network に、固定の IPv6 アドレスでつなぐ構成を、既定の compose を変えずに override のファイルとして用意する。

- Docker はプレフィックスを知らないので、Docker にアドレスを割り当てさせる方法（`--ip6`）は使えない。
  endpoint の sysctl を指定する driver option で、そのコンテナのインターフェースだけ IPv6 を有効にし、
  `ip token` でインターフェース ID を固定する。RA のプレフィックスとこの ID からアドレスが決まる。
- `ip token` には `NET_ADMIN` が要る。natsumi 本体に capability を足さず、ネットワークの名前空間だけを持つ小さなコンテナに
  `NET_ADMIN` だけを与える。このコンテナも読み取り専用のルートファイルシステムと `no-new-privileges` で動かす。
  natsumi 本体は `network_mode: service:` でその名前空間を共有し、非 root・全 capability なしのままとする。
  本体を再起動しても名前空間は残るため、アドレスも変わらない。
- 名前空間のコンテナは、トークンを設定したあと、トークンで終わるグローバルアドレスが使えるようになるまで待つ。
  設定に失敗した場合、決められた時間内にアドレスができない場合、重複アドレス検出に失敗した場合は、エラーを出して終了する。
  ヘルスチェックでアドレスの有無を確かめ、natsumi 本体はそれが正常になってから起動する。IPv6 のアドレスなしで黙って動かさない。
- 非 root のまま 80 / 443 で待ち受けるため、capability ではなく、名前空間ごとの sysctl `net.ipv4.ip_unprivileged_port_start` を 80 にする。
  この sysctl は IPv6 の待ち受けにも効き、影響はその名前空間の中に限られる。
- 公開する override には、network 名・トークン・ドメインの実際の値を書かない。
  network 名とトークンは必須の環境変数とし、未設定なら compose が止まる。ドメインは natsumi の設定ファイルに書く。

## Consequences

- ファイアウォールで、公開するアドレスへの tcp 443 と tcp 80 を通す必要がある。
- ACME のコードを自分で保守する。CA の仕様変更で取得できなくなった場合、古い証明書が切れる前にログで気づいて対応する必要がある。
- 証明書とアカウント鍵は data directory の一部としてバックアップする。失うと新しいアカウントで再発行することになり、
  CA のレート制限に当たることがある。試験には staging を使う。
- 初回起動時、証明書を取得するまで HTTPS に接続できない。
- 名前空間のコンテナを再作成すると、natsumi 本体も再起動し、短時間つながらなくなる。
- 名前空間には、トークンのアドレスのほかに自動設定のアドレスが残ることがある。外向きの通信の送信元はそちらになり得る。
  外から届くのはトークンのアドレス（DNS の AAAA）である。
- 実際の Let's Encrypt との疎通、RA が配られる network でのアドレスの確定は、ファイアウォールを設定したあとの本番環境で確かめる。
  自動テストはローカルの模擬 CA で行う。

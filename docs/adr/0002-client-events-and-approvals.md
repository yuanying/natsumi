# 0002. 会話・承認・通知のサーバー契約

- Date: 2026-09-14
- Status: Accepted（会話の配信・busy・snapshot の作り方は [ADR 0008](0008-single-thinking-loop-and-mac-conversation.md) で置き換え）

## Context

複数端末の同時操作や再接続により、会話送信、承認、通知が重複し得る。
外部サービスへの許可とクライアント認証は、会話の表示や Pi の内部通信と分離する必要がある。

## Decision

Mac とサーバーの接続は HTTPS/WSS とし、IPv6 からも到達可能にする。
GitHub 認証を必須にし、設定した単一アカウントだけを許可する。
OAuth の state と PKCE、短期セッションを使い、callback と WebSocket upgrade の双方で検証する。
GitHub が返す本人情報で allowlist を照合し、ログイン名変更に備えて確認済みの数値 ID を保存する。
クライアントの自己申告ユーザー名は認証に使わない。異なる ID は接続を拒否する。
サーバーの Pi/Google 認証は GitHub 認証と別管理とする。
Pi SDK はサーバー内部に閉じ、Mac に任意の SDK 呼び出しやローカルパスを渡す口を公開しない。

アプリ独自の `v: 1` 契約で会話・承認・通知を配信する。
具体的な envelope と復旧手順は [client-contract.md](../client-contract.md) に定める。
サーバーが会話操作 を直列化し、会話表示に必要な Pi イベントだけを変換して全端末へ配信する。
request ID により送信再試行を重複排除する。処理中の別メッセージは busy として返し、クライアントで保持する。
配信 sequence は登録端末ごとの stream 内で採番し、その stream の再接続中の欠落検出に使う。
端末限定配信は他端末の sequence を進めない。会話本文の永続イベントログは作らない。
サーバー再起動・イベント欠落時は Pi から snapshot を読み直す。

承認は具体的な予定変更の全内容とその revision に結び付ける。
期限切れ、内容変更、対象予定の更新があれば旧承認を無効化し、再承認する。
複数 Mac からの同時承認は SQLite の条件付き更新で一件だけ受理する。
Calendar 削除と参加者への招待送信は、方針未決定のため無効とする。
Calendar 作成・変更の許可を、任意の shell 実行や別変更への包括許可に変換しない。

通知はサーバーが受理した最後の明示操作の端末へ送る。
heartbeat やバックグラウンド再接続で「最後に操作した端末」を更新しない。
対象が切断していれば最新操作順で接続中の端末を選び、全端末がオフラインなら永続保留する。
次に接続した端末へ保留分をまとめて送り、通知 ID の ACK をサーバーで一度だけ記録する。
配信は at-least-once とし、再送時の表示重複をクライアントの通知 ID で抑える。

## Consequences

認証拒否、複数端末の競合、期限切れ承認、通知 ACK 消失と再配信を実装試験に含める。
ネットワークと外部 API をまたぐ exactly-once は仮定せず、結果不明時は照合後に再開する。
この PR の fixture は Pi SDKの検証であり、これらの本体動作が実装済みであることは意味しない。

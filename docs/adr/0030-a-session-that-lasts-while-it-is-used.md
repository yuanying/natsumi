# 0030. 使っている間は切れないクライアントのセッション

- Date: 2026-09-23
- Status: Accepted（クライアントが期限を受け取って Keychain の期限を延ばす対応は、Mac と iPhone の両方に入った）

## Context

[ADR 0006](0006-github-login-and-transport.md) では、クライアントのセッションの寿命を発行から 12 時間とし、refresh を持たなかった。
切れたらクライアントは GitHub のログインをやり直す。ADR 0006 の Consequences には、
12 時間ごとの再ログインが煩わしければ寿命や refresh を後で見直す、と書いてある。

見直す理由は 2 つある。

- Mac は常駐して接続し続けるので、12 時間ごとにログインの画面が出る。
- iPhone への通知は、失効・取り消しされたセッションの端末には送らない。iPhone のアプリを 12 時間開かないだけで、
  通知が止まる。

本人の決定は、セッションを「使うたびに延ばす」（sliding expiration）ことである。
次を決める必要がある。

- 寿命の長さと、「使った」の定義
- 接続し続けている間の延ばし方と、DB に書く回数の抑え方
- 延びた期限をクライアントに知らせる方法。いまのクライアントは、手元に保存した `expiresAt` で期限切れを判断している
- 期限切れの接続を定期的に閉じる処理、ログアウトによる即時の失効、平文のトークンを DB に置かない方針との関係

## Decision

### 寿命は最後に使ってから 30 日

- セッションは、最後に使ってから 30 日で切れる。使うたびに、期限を「その時刻から 30 日後」に動かす。
- 期限の上限（発行から何日で必ず切れるか）は設けない。使い続ける限り、ログインはやり直さなくてよい。
- 30 日は、しばらく iPhone を開かない期間（旅行や、Mac だけで過ごす週）をまたいでも通知が止まらない長さとして選んだ。
  一方、1 か月まったく使わなかった端末は手放した可能性があるので、そこで切る。

### 「使った」とは、認証の通った接続と、接続し続けていること

- WebSocket の upgrade でセッションが認証を通ったとき、そのセッションを使ったことにする。
- 接続が開いている間も、使い続けていることにする。サーバーは期限切れの接続を閉じる定期の処理（30 秒ごと）で、
  開いている接続のセッションを延ばす。
- ログアウトの要求（`POST /auth/logout`）は延長しない。これから失効させるセッションだからである。
- command を受けるたびには延ばさない。接続が開いていれば、定期の処理が延ばす。

### DB への書き込みは 1 時間に 1 回まで

- 延長は、前回の延長から 1 時間以上たったときだけ書き込む。期限が「今から 30 日後」より 1 時間以上手前にあるときだけ、
  `expires_at` を書き換える。1 時間未満なら何も書かず、いまの期限をそのまま返す。
- 定期の処理は 30 秒ごとに走るが、書き込みはセッションあたり 1 時間に 1 回にとどまる。その代わり、期限は最大で
  1 時間ぶん短く見積もられる。30 日の寿命に対しては無視できる。
- 最後に使った時刻を別の列に持たず、`expires_at` を書き換えるだけにする。migration は要らない。

### 延びた期限はクライアントに知らせる

クライアントは手元の期限で「切れたかどうか」を判断するので、延びた期限を知らせる。

- `session.sync` への答え（`session.snapshot`、再送の `command.accepted`、`service.unavailable`）に `sessionExpiresAt` を付ける。
  接続した時点での延長を反映した期限である。
- 接続中に期限が動くと、サーバーはその接続に `session.renewed`（`expiresAt`）を送る。同じセッションの別の接続が延ばした場合も届く。
- `session.renewed` は `conversation.thinking` と同じく、その場限りの event とする（[ADR 0017](0017-streaming-the-line-she-is-thinking.md)）。
  seq を消費せず、再送のバッファに入れず、その stream がいま出している seq を付けて送る。
  この event を知らないクライアントは、すでに受け取った seq として捨てる。同期の前に届いても、stream の位置を持たないので捨てる。
  セッションは接続ごとのものであり、端末の stream で番号を取って再送すると、再ログインした後の端末に古いセッションの期限が届き得るためである。
- `sessionExpiresAt` と `session.renewed` の値は、クライアントが持っている期限より後のときだけ採る。
  延長は期限を必ず後ろに動かし、新しいログインのセッションは古いものより後に切れる。したがって、再送で古い snapshot が届いても、
  手元の期限は戻らない。

### 古いクライアントとの互換

- 新しい欄と event を知らないクライアントは、今までどおり受け取った `expiresAt`（ログインから 30 日後）で判断する。
  そのクライアントを使い続けても、サーバー側のセッションは延び続けるので、30 日で再ログインするだけで壊れない。
- 契約の変更は、欄と event の追加だけである。protocol version は上げない。

### 期限切れ・取り消しとの関係

- 定期の処理は、延長を試みた結果でセッションが生きているかを知る。取り消されたか、すでに期限を過ぎていたセッションは延ばさず、
  その接続を close code 1008 で閉じる。期限を過ぎたセッションを延長で生き返らせることはしない。
- ログアウトは今までどおり、そのセッションを即時に失効させ、開いている接続を閉じる。
- command を受けるたびに、接続が知っている期限を確かめる規則はそのまま残す。
- `client_sessions` にはトークンの SHA-256 だけを置く方針を維持する。延長は `session_id` で行い、トークンを扱わない。

これにより、ADR 0006 の「寿命は 12 時間とし、refresh は持たない」を置き換える。

## Consequences

- **トークンが漏れたときに使える期間が延びる。** 12 時間で自然に切れていたものが、盗んだ側が使い続ける限り切れない。
  上限を設けないので、失効させる手段はログアウトと、設定の `allowedUserId` を変えること（すべてのセッションが使えなくなる）だけになる。
  端末をなくしたときにその端末のセッションだけを取り消す手段（セッションの一覧と個別の失効）は、まだない。必要になったら足す。
- 古いクライアントは、ログインから 30 日たつと手元でトークンを捨てて再ログインする。捨てたセッションはサーバーでは生きたままだが、
  使われなければ 30 日で切れ、次のセッションの発行時に掃除される。
- この変更の前に発行した、12 時間の期限のセッションは、次に接続したときに 30 日へ延びる。すでに切れていたものは延びない。
- 変更を戻す場合、延びた期限は DB に残り、戻した後のサーバーでも最長 30 日有効なままになる。
  すぐに 12 時間の寿命へ戻したいときは、`client_sessions` の `expires_at` を切り詰める。
- クライアントは、`sessionExpiresAt` と `session.renewed` を受け取って Keychain の期限を更新する必要がある。
  それまでは、Mac と iPhone は 30 日ごとに再ログインする。
